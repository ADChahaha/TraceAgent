# 核心工程原则（Core Beliefs）

归属 [设计文档总目](index.md)，记录本仓库跨包通用的工程品味与底线。当具体任务未逐项指定实现细节时，按下列原则取舍。

## 1. 面向增加、谨慎修改

- 新能力、新文档格式或新扩展点优先通过新增独立模块承接，尽量减少对既有稳定逻辑的侵入式改动，同时避免无意义的提前抽象。
- 动手前必读目标模块 `DECISIONS.md`；当新需求与旧模块已有决策冲突时，优先新增模块或显式扩展，不静默改坏旧契约。

## 2. 验收驱动、测外部行为

- 需求先整理为用户可观察的验收标准并确认再动手；优先用接口契约、集成测试、故障复现和真实端到端验证锁定结果，不以贴近内部实现的微粒度单测代替行为验收。
- 跨服务、并发或高风险改动在自验后增加一次独立视角的只读核查，降低自评偏差；涉及协议联调或前端交互的改动尽量做真实运行态验证，不只依赖 Fake/Mock。

## 3. 边界显式校验，损坏直接拒绝

- 数据进入系统边界时显式校验格式、配额与路径安全（如存储桶/键白名单、资源引用归属、请求参数校验），不靠隐式猜值或宽容兜底吞错。
- 遇到已持久化产物或索引损坏时显式报错拒绝，不静默回退全量重建，避免悄无声息破坏历史引用编号或状态一致性。

## 4. 单源真相与清晰所有权

- 每类状态与知识只保留一个权威来源：对话稳定历史以 `backend` SQLite 经 `crud.transaction()` 原子提交的 `chat_messages` 为准；前端投影以 `GET /resume` 快照为准；文档与记忆各自按单源维护，其他位置只留简短指针。
- 服务间通过显式协议与对象存储边界解耦，不跨服务直接 import 内部模块，不把网络 I/O 等待与会话状态写锁混在一起。

## 5. 机械门禁优于口头提醒

- 长期生效的决策必须写明三要素（做了什么决定、为什么这么选、排除了哪些备选方案）并落入对应模块 `DECISIONS.md`；凡能转成结构测试、打包测试或审计脚本的不变量，优先用自动化门禁锁死，而不是仅留在文字规范里。
